# UI 调试

项目命令在 WSL 执行，浏览器通过实际页面操作验收。需要独立调试 task 时，主 task 负责仓库和服务，调试 task 负责浏览器复现、复验及自身工作目录清理。

## 1. 准备服务和验收范围

读取根目录 `AGENTS.md`、`docs/development.md`，按问题查阅 `DESIGN.md`、对应游戏设计文档与实现。明确目标页面、复现步骤、预期行为和需要覆盖的交互。

复用已经运行的项目服务；需要启动时，从 Windows/PowerShell 调用：

```powershell
wsl.exe -d Ubuntu-24.04 --cd /home/tong/projects/maker-simulator bash -ic 'pnpm run dev --host 0.0.0.0 --port 5173 --strictPort'
```

使用 WSL 内的 Node.js 和 pnpm，通过 `bash -ic` 加载开发环境。确认实际端口和服务输出，把可访问的完整 URL 交给调试 task，例如 `http://localhost:5173/games`。HTTP 响应正常只能证明服务可访问，不能代替页面验收。

## 2. Windows 本地调试 task

本项目的 WSL UNC 工作区曾导致 Windows 沙箱在工具初始化阶段处理目录权限失败；即使内置浏览器已经打开，浏览器工具也可能尚未执行就失败。遇到这一情况，将浏览器操作放到 Windows 本地目录中的独立 task。项目源码和开发服务继续留在 WSL。

- 已有本次工作使用的 Windows 本地调试 task 时，复用它。需要查找时使用 `list_threads`，用 `read_thread` 确认用途和状态。
- 新建独立 task 必须已有用户的明确要求或授权；会话内已授权时直接继续。调用 `create_thread`，使用 `target.type: projectless` 和本次调试专属的 `directoryName`。
- 由调试 task 确认并回报自身实际 host 工作目录。该目录必须是专用于本次调试的 Windows 本地目录，不能复用 WSL 仓库目录或共享工作目录。
- 主 task 记录返回的 `threadId`、`hostId`。通过 `send_message_to_thread` 发送修复后的复验要求，用 `wait_threads` 等待结果并复用 cursor，避免反复读取完整历史。

调试 task 的初始 prompt 必须自包含，至少写明：

- 实际服务 URL、验收范围、复现步骤和已知的存档/检查点信息；
- 主 task 的 id，以及发现问题后回报证据、等待修复后复验的协作方式；
- 使用内置浏览器和当前可用的 CUA 工具；项目命令与代码修改由主 task 在 WSL 中完成；
- 下文的浏览器操作、存档保护及完整清理要求。

将这些要求直接写进 prompt，不能只发送本 skill 的 WSL 文件路径。Windows 本地调试 task 无需读取仓库文件即可操作已运行的页面。

## 3. 页面复现与复验

按浏览器工具当前返回的文档使用 API。需要查找已打开页面时，首次调用只执行 `await cua.getState()`，读取结果后再选择匹配的内置浏览器标签页；有可用页面时优先复用。

- 通过页面点击、输入、滚动和键盘操作复现，观察实际渲染、焦点、禁用状态和操作结果。不为这套验收流程新增 UI 自动测试文件。
- 随问题覆盖桌面、窄屏和键盘交互；检查说明是否可见、按钮是否可达、操作后页面和数据是否一致。只将实际执行并观察过的项目标记为通过。
- 优先新建专用测试存档，或从合适的稳定检查点创建测试分支。随机问题记录 `profileId`、`runId`、`turnId` 和操作顺序，复验时复用可重现的起点。不要为方便复现而清空已有 IndexedDB 或修改用户存档。
- 需要解释游戏行为时，查看控制台和 `?runtimeMonitor=1`；需要更细日志时使用 `?runtimeMonitor=verbose`。记录有关的命令、Action、Reaction id 和参数，以及操作前后的属性变化。
- 回报问题时给出页面/路由、前提、操作、预期、实际结果和相关日志。截图可作为调试中的临时证据；未覆盖的分支、终局或设备明确列出。

主 task 根据证据确定问题属于 UI、Gameplay 还是游戏内容，再修改对应部分。属于游戏内容的规则或文案问题只修改游戏包与写作相关文档，使用仓库的 `write-story-script` skill；这类修复不额外新增集成测试。通用 Runtime、持久化等语义确有变化时，再按根目录规范验证。

修复后把变更范围和目标路径发给原调试 task，在实际页面复验原始失败路径及受影响的相邻操作。以实际页面结果确认修复，不以代码检查或构建成功代替。

## 4. 完成后完整清理 host 工作目录

每轮 UI 调试或复验结束、交付结果之前，**调试 task 必须完全清空自己的 host 工作目录**。产物和工作过程中的衍生物一并删除，包括截图、录屏、报告、日志、下载、临时脚本、缓存、临时依赖、隐藏文件和所有子目录；只清理 `outputs/` 不算完成。

清理按以下顺序完成：

1. 将验收结论、复现步骤、已验证及未覆盖事项发回主 task，保存在任务对话中。不要把文件搬到其他目录或打包备份来规避清理，最终回复不引用即将删除的本地产物。
2. 停止仅由本调试 task 启动且已不再需要的辅助进程，释放文件占用；从工作目录之外执行清理。
3. 在 Windows PowerShell 中解析实际绝对路径，与调试开始时记录的专属工作目录精确核对。确认目标不是盘符根目录、用户主目录、工作目录的父目录、WSL 仓库或共享目录。
4. 使用原生 PowerShell 的 `Get-ChildItem -LiteralPath ... -Force` 枚举全部内容。递归删除前核实每个目标都位于该专属目录内，使用 `Remove-Item -LiteralPath` 删除；遇到符号链接或 junction 只删除链接本身，不递归进入其目标。文件操作全程使用同一 shell，不把枚举出的路径交给 `cmd /c` 或拼接的 shell 命令。
5. 清空目录内容，保留空的工作目录即可。若曾在目录外创建临时文件，依据本 task 的创建记录逐项清理，不能扩展为删除 host 的共享缓存、浏览器数据或其他 task 的文件。
6. 再用 `Get-ChildItem -LiteralPath ... -Force` 核实目录为空，在结果中报告清理的绝对路径和剩余项数量。删除失败、权限不足或仍有残留时，说明具体阻塞，不能宣称调试已全部完成。

主 task 收到清理结果后再完成交付：说明修复范围、页面复验结果、仍未覆盖的事项，以及调试 task 工作目录已清空。
